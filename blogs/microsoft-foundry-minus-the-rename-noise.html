Local government does not need another AI product name. It needs a supportable way to build secure, governed, maintainable AI services.

What Microsoft Foundry is - and why municipalities should care

Microsoft Foundry is Microsoft’s Azure platform for building and operating custom AI applications and agents. It brings models, agents, organizational knowledge, specialized AI services, evaluation, monitoring, and governance capabilities into a more cohesive development and operating model.

For municipalities, the value is not the product diagram. It is the ability to assemble these capabilities without treating every proof of concept as a separate, one-off experiment.

The practical definition
Foundry supplies managed AI capabilities and operating surfaces. Your team still owns the application experience, business rules, authoritative data, security design, records obligations, human approvals, accessibility, and cost controls.

First: what happened to Azure AI Foundry?

The naming has genuinely been confusing. At Microsoft Ignite in November 2024, Microsoft introduced Azure AI Foundry, with the portal replacing what had previously been called Azure AI Studio. Current Microsoft documentation reflects the progression:

Azure AI Studio → Azure AI Foundry → Microsoft Foundry

By Ignite 2025, Microsoft was using the Microsoft Foundry name across models, agents, knowledge, tooling, and governance announcements. More importantly, the newer architecture centers on Foundry resources and projects. Older hub-based projects still exist through the classic experience, so teams that experimented earlier should verify which project architecture they are using before expanding it.

The platform in one picture

The cleanest way to understand the platform is to separate what the municipality builds from what Foundry manages and what remains a separately governed Azure resource.

What is actually inside Microsoft Foundry?

1. Foundry Models

Foundry Models is the discovery, evaluation, and deployment layer for models from Microsoft, Azure OpenAI, Anthropic, Meta, Mistral, Cohere, Hugging Face, and other providers. Microsoft documentation and product pages currently describe a catalog exceeding 10,000 models.

That number needs context. Models differ by provider terms, region, deployment type, lifecycle, pricing, safety behavior, and government-cloud availability. A catalog entry does not guarantee that a model is available in every region or project type.

The better selection question
Do not ask, “How many models can we access?” Ask, “Which model meets this workload’s security, cost, performance, support, and governance requirements?”

2. Foundry Agent Service

Foundry Agent Service is the managed environment for building and operating agents. Prompt agents are largely configured through models, instructions, and tools. Hosted agents let developers bring custom code and orchestration, including supported agent frameworks.

Foundry does not eliminate application development. Your team still owns the user experience, APIs, deterministic business rules, integrations, exception handling, human approvals, source control, and deployment pipelines.

3. Foundry IQ and organizational knowledge

Foundry IQ should not be described as Azure AI Search renamed. It is a managed knowledge layer built on Azure AI Search that helps agents retrieve and reason over organizational information. Azure AI Search still exists independently and remains appropriate for custom RAG architectures.

For government, the stronger pattern is not to let a model “know everything.” Give it controlled access to authoritative sources, enforce permissions, return citations, and maintain clear content ownership and refresh processes.

4. Foundry Tools

Foundry Tools is the current umbrella for capabilities many Azure developers previously knew as Azure AI Services or Cognitive Services. This includes Document Intelligence, Content Understanding, Vision, Speech, Language, Translator, Content Safety, and Azure AI Search. These remain separately metered capabilities with their own APIs, regions, limitations, and pricing.

Where the developer boundary sits

A useful architecture boundary is simple: developers build the application and domain logic; Foundry provides managed AI infrastructure around it.

The municipality and development team own Foundry can manage
User experience and accessibility Model deployments and inference
APIs and integration contracts Prompt-agent or hosted-agent runtime
Business rules and approvals Agent identities, endpoints, and tools
System-of-record transactions Knowledge retrieval and grounding
Source control, ALM, and support model Tracing, evaluation, and guardrails

A safe municipal AI pattern

The safest production pattern keeps approved source data, AI assistance, staff validation, and the authoritative transaction visibly separate.

What could a municipality actually do with it?

Document and records intelligence

Document Intelligence or Content Understanding can extract structured information from permit packets, inspection reports, invoices, meeting materials, archived forms, and supporting attachments. The output should enter a review queue rather than silently becoming an official record.

Grounded internal knowledge

A municipality can ground an internal assistant in approved policies, procedures, ordinances, engineering standards, or program guidance. Citations and permission-aware retrieval improve verifiability, but the municipality still owns source freshness, access cleanup, records classification, and content stewardship.

Inspections and infrastructure

Vision, Content Understanding, and language models can assist with sewer CCTV review, asset-image classification, inspection-note summarization, and suspected-defect triage. AI can focus an inspector’s attention; it should not independently become the official engineering, compliance, or public-safety determination.

Permitting and resident services

A resident-facing service could explain requirements, identify potentially missing documents, translate approved guidance, or retrieve case status through a controlled API. Approvals, denials, fees, enforcement actions, and official case changes should remain behind deterministic rules and accountable review.

Bounded internal agents

A prompt agent may be enough for a staff assistant that retrieves approved guidance and calls a small set of controlled tools. Use a hosted agent when custom code, specialized orchestration, or framework-specific behavior is genuinely required. Do not start with a multi-agent architecture merely because the platform supports one.

Public-sector design rule
Use AI to reduce reading, searching, extracting, summarizing, and triage effort. Keep consequential decisions, authoritative transactions, and exceptions under accountable human control.

What to check before starting

  1. Use case and authority. Define what the system may retrieve, recommend, draft, or execute - and what always requires staff confirmation.
  2. Identity and least privilege. Prefer Microsoft Entra ID, managed identities, and narrowly scoped Azure RBAC. Treat every tool call and connected data source as a separate permission decision.
  3. Data and network boundaries. Confirm processing location, model deployment type, private connectivity, outbound paths, and the independent controls on Search, Storage, Key Vault, databases, and municipal systems.
  4. Tracing, audit, and records. Decide what prompts, responses, citations, tool calls, approvals, and generated artifacts must be logged or retained. Traces may contain resident, employee, or case data, so minimize access and set deliberate retention.
  5. Quality and responsible AI. Test groundedness, missing information, prompt injection, unsafe tool use, accessibility, inconsistent treatment, and low-confidence behavior using representative municipal scenarios.
  6. ALM and cost controls. Separate development, test, and production. Version prompts, agent definitions, tools, evaluation datasets, policies, and infrastructure. Budget for separate meters across models, Search, tools, hosting, storage, monitoring, and networking.

Where I would start

Do not begin with, “Where can we deploy an AI agent?” Begin with:

A better starting question
Where are employees spending significant time reading, searching, extracting, summarizing, or validating information?

Choose one bounded process. Give the AI only the information and tools it needs. Keep the existing system of record authoritative. Measure accuracy, staff time saved, failure cases, and cost under realistic traffic. Expand only when the evidence supports it.

The practical takeaway

Microsoft Foundry matters to local government because it provides a more coherent Azure foundation for custom AI services - not because the name changed.

It brings models, managed and code-based agents, knowledge retrieval, specialized AI services, evaluations, observability, and governance into a more unified operating model. But the municipality still owns the hard parts: lawful purpose, identity, authoritative data, accessibility, records retention, consequential decisions, cost, and accountability.

Start small. Govern deliberately. Scale with evidence.
Use the simplest capable component, keep systems of record authoritative, and require human validation whenever an outcome affects a resident, public asset, fee, eligibility decision, enforcement action, or public-safety determination.
