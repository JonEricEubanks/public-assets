Building an AI agent is getting easier. Building an agent system that knows which agent should act, what context to share, when the work is done, and where a person must approve is the harder architectural problem.

That is what multi-agent orchestration is for, and the word is borrowed from music on purpose. An orchestra is not the most instruments you can fit on a stage. It is a set of sections, each playing only its own part, following one score, under one conductor who never picks up an instrument but decides when the piece is finished. Hold that picture; every figure in this post uses it. The agents are the sections. The workflow is the score. The amber seal is the conductor.

Microsoft Foundry Agent Service is the managed platform: models, tools, identity, runtime, observability, evaluations, publishing. Microsoft Agent Framework supplies the orchestration patterns that decide how specialized agents collaborate on that platform.

The goal is not the most agents. It is the least complex architecture that completes the work reliably, securely, and economically.

Foundry is the platform, not the pattern

Keep the two separate. Foundry supplies the operational foundation:

  • Models from the Foundry catalog
  • Prompt agents and hosted agents on a managed runtime
  • Tool access, including MCP servers and custom functions
  • Microsoft Entra identity and role-based access control
  • Tracing, metrics, evaluations, and Application Insights
  • Agent versioning and publishing

The orchestration pattern decides how agents divide, route, review, and finish the work. Agent Framework ships five: sequential, concurrent, handoff, group chat, and Magentic. You can also define custom workflows from executors, edges, routing rules, and events.

Start with one agent

Multi-agent is not the default. Microsoft recommends the lowest level of complexity that reliably meets the requirement. A direct model call may cover a focused transformation. A single agent with tools is the usual enterprise default for work inside one domain. Orchestration earns its place when work crosses domains, needs parallel specialization, benefits from separate security boundaries, or one agent has collapsed under too many instructions, tools, and knowledge sources.

A separate agent is easier to justify when the capability:

  • Has a distinct set of tools or knowledge
  • Requires a different security boundary
  • Has a reusable responsibility
  • Needs to be evaluated independently
  • Is maintained by a separate team

If none of those apply, another agent adds coordination cost, not value.

1. Sequential orchestration

Work passes through agents in a fixed order; each processes the previous agent's output. Microsoft also calls this a pipeline, prompt chaining, or linear delegation. The route is deterministic, not chosen by the agents.

Use it when:

  • Stages have clear dependencies and must run in order
  • Each stage progressively improves the last one's output
  • Routing must be predictable
  • A human approval gate belongs at a defined point

For a municipal records request: one agent classifies, one extracts search criteria, one checks policy requirements, and a final agent drafts the response for human review. The workflow enforces the stages; agents perform bounded reasoning inside them.

2. Concurrent orchestration

The same request goes to several agents at once. Each works independently; results are collected, compared, or synthesized afterward. Also known as fan-out/fan-in, scatter-gather, or map-reduce. The merge can be rules, voting, weighted combination, or model-based synthesis.

Use it when:

  • Work can be done independently and in parallel
  • Multiple professional perspectives are needed
  • There is a clear conflict-resolution strategy
  • Agents do not need to update the same mutable state

In the public sector, concurrent agents should return structured findings rather than each writing to the authoritative record. A coordinating workflow validates and combines them before committing to Dataverse or another system of record.

3. Handoff orchestration

One active agent transfers control to a specialist, often only after the request reveals which domain it belongs to. Also called routing, triage, transfer, dispatch, or delegation. Only one specialist owns the request at a time, and a path back to staff is a designed exit, not a failure.

A reliable handoff needs more than an agent description. Define why the transfer happened, what context is authorized to move, who owns the next step, who delivers the final response, what happens if no specialist accepts, and when the system escalates to a person.

Connected agents were the classic Foundry way to do this. Microsoft has marked classic agents deprecated with retirement on March 31, 2027; new work should use the generally available Agent Service and current workflow capabilities.

4. Group chat orchestration

Several agents share an accumulating conversation while a chat manager picks who speaks next and steers toward a result. Also a roundtable, council, or debate pattern, and the natural fit for maker-checker review.

The loop is simple: a maker produces an artifact, checkers evaluate it against defined criteria, the maker revises, and the loop stops on approval or an iteration limit that keeps the transcript from accumulating forever. Anything unresolved goes to a person. Microsoft recommends clear acceptance criteria, iteration limits, and fallback behavior, and notes coordination gets hard fast; three agents or fewer is the guidance.

In government scenarios, position group chat as review and advice. Agents flag policy conflicts, accessibility issues, or missing evidence; an authorized employee stays accountable for the decision.

5. Magentic orchestration

For open-ended tasks where the path cannot be known up front. A manager agent builds a plan, assigns specialists, watches progress, detects stalls, and replans as it learns. Also called dynamic, adaptive, or task-ledger orchestration.

Microsoft Research's Magentic-One keeps a Task Ledger for facts and plans and a Progress Ledger for assignments and status, revising the plan when progress stalls. Do not reach for it because it is the most autonomous. It is the wrong tool for low-complexity, time-sensitive, or already-well-defined work, and its dynamic planning makes cost and behavior harder to predict.

Why hybrid usually wins

Most government processes mix deterministic and nondeterministic work. A permit review needs agents to interpret documents, extract conditions, search policy, and explain findings. It also has mandatory review stages, approval authorities, notification requirements, and retention obligations that should never depend on agent discretion.

  • Foundry agents interpret, classify, research, and recommend
  • Agent Framework coordinates the reasoning
  • MCP or controlled tools expose bounded data and actions
  • Dataverse holds authoritative process state
  • Power Automate or Logic Apps runs deterministic integration steps
  • Human reviewers approve consequential decisions
  • Application Insights and Foundry evaluations watch the whole thing

This is an architectural recommendation, but it lines up with Microsoft's guidance on least privilege, durable state, human participation, security trimming, output validation, and end-to-end observability.

Governance is designed in, not bolted on

Every added agent multiplies model calls, tool interactions, context transfers, and failure points. A production Foundry architecture covers four areas.

Identity and authorization

Each agent gets only the models, knowledge, and tools its responsibility requires. No connected or hosted agent may become a path around the requesting user's authorization boundary.

State and context

Do not forward full conversation history by default; pass the minimum the next step needs. Externalize long-running state so execution resumes instead of replaying. Compact and prune as transitions accumulate.

Reliability

Transitions need timeouts, retries, output validation, checkpoints, circuit breakers, and graceful degradation. A malformed result from one agent must not become trusted input for another.

Observability and evaluation

One trace should connect the user request, parent agent, child agent, model call, tool call, approval checkpoint, and final outcome. Cost belongs in the same view: every added agent is another set of model calls to pay for.

Final takeaway

The right Foundry architecture is rarely the one with the most agents. It uses the fewest agents necessary, gives each a distinct responsibility and limited authority, matches the pattern to the work, and wraps deterministic controls around anything that touches people, records, money, or public services.

Each pattern is a different way to arrange the sections. Sequential plays them one after another. Concurrent has them play at once and resolves the chord. Handoff passes the melody to whichever section the piece calls for. Group chat lets sections rehearse a passage until it meets the score. Magentic lets the manager rewrite the score mid-performance. Foundry is the hall: the stage, the acoustics, the lights, the recording that proves what was played.

The future is not one agent that does everything. It is a governed team of specialists that knows how to work together, when to ask for help, and where its authority ends. The sections play. The conductor decides.
